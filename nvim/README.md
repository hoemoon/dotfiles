# Markdown workbench (Neovim 0.12)

A setup for writing markdown and developing Lua (Neovim plugins).
Rebuilt from scratch on 2026-08-08 after re-evaluating the ecosystem.

- **Neovim**: 0.12.4 (Homebrew)
- **Plugins**: 9, managed by the built-in `vim.pack`
- **Startup**: ~31 ms (no lazy loading — everything loads immediately)

```
~/.config/nvim/
├── init.lua                    entry point — requires in order
├── lua/config/
│   ├── options.lua             global options · treesitter · autocommands
│   ├── plugins.lua             vim.pack.add + per-plugin setup
│   ├── completion.lua          completion (0.12 built-in)
│   ├── lsp.lua                 vim.lsp.enable · LspAttach keymaps · diagnostics
│   ├── keymaps.lua             global keymaps
│   └── ime.lua                 Korean/English IME switching (macOS)
├── lsp/                        per-server config — loaded by vim.lsp.enable
│   ├── lua_ls.lua
│   ├── markdown_oxide.lua      notes (PKM)
│   └── harper_ls.lua           (disabled)
├── after/ftplugin/markdown.lua markdown = prose settings
└── nvim-pack-lock.json         generated by vim.pack (commit it)
```

## 1. Solved without plugins — Neovim 0.12 built-ins

The central judgment behind this config. **Four things that needed a plugin in
2025 are now in core.**

| Capability | Built-in API | Plugin dropped |
|---|---|---|
| Plugin management | `vim.pack` | lazy.nvim |
| Syntax highlighting | `vim.treesitter.start()` | nvim-treesitter (and its whole parser build system) |
| LSP client config | `vim.lsp.config` / `vim.lsp.enable` | nvim-lspconfig, mason-lspconfig |
| Snippet expansion | `vim.snippet` | LuaSnip, friendly-snippets, cmp_luasnip |
| Installing LSP binaries | (brew) | mason.nvim, mason-lspconfig |
| Injecting Lua libraries | `workspace.library` set directly | lazydev.nvim (used 205 MB more memory) |
| **Completion** | `'autocomplete'` + `'complete'` + `vim.lsp.completion` | **blink.cmp** (nvim-cmp + 6 sources before that) |

### treesitter — parsers ship with the binary

nvim 0.12 bundles these parsers:

```
markdown  markdown_inline  lua  vim  vimdoc  query  c
→ /opt/homebrew/Cellar/neovim/0.12.4/lib/nvim/parser/*.so
```

That is exactly the set a markdown-and-Lua workflow needs, so `nvim-treesitter`
is unnecessary. A `FileType` autocommand in `lua/config/options.lua` calling
`vim.treesitter.start()` is the entire integration.

> Side benefit: nvim-treesitter did a full `master`→`main` rewrite in March 2026,
> and the new version compiles parsers locally via the tree-sitter CLI. This skips
> that migration entirely.

### LSP — the `lsp/<name>.lua` convention

Calling `vim.lsp.enable("markdown_oxide")` makes Neovim search the runtimepath for
`lsp/markdown_oxide.lua` and read it. That is why server configs live in a
top-level `lsp/` rather than under `lua/`.

### Re-reading files changed outside nvim

In `lua/config/options.lua`. **When Claude Code, another terminal, or a git
checkout modifies a file, the nvim buffer still shows the old contents — and
saving from that state overwrites someone else's change.**

`'autoread'` alone is not enough. It is only a policy ("re-read when a change is
detected"); **when the check happens** is a separate question. nvim does not watch
files, it checks at specific moments, and in a terminal those moments rarely
arrive.

```lua
vim.api.nvim_create_autocmd({ "FocusGained", "BufEnter", "CursorHold", ... }, {
  callback = function()
    vim.schedule(function() vim.cmd.checktime() end)   -- ★ schedule is required
  end,
})
```

> **`vim.schedule` is the crux.** `:checktime` defers its check while an
> autocommand is running, so as not to swap a buffer mid-flight. It has to run
> outside the autocommand to take effect immediately. Omitting it produces a
> hard-to-diagnose symptom: the callback fires but the file never updates.

`updatetime` is 250 ms, so pausing the cursor briefly picks up the change. A
notification appears when a file is re-read.

> Going further, there is `coder/claudecode.nvim` (3.0k★), which implements the
> same WebSocket MCP as the VS Code extension: instead of writing files silently,
> Claude **proposes changes in an nvim diff window**, accepted with `:w` and
> rejected with `:q`. It pays off once the workflow moves to running Claude inside
> nvim (and it pulls in snacks.nvim).

### Completion — `'autocomplete'` is new in 0.12

Configured in `lua/config/completion.lua`.

```lua
vim.o.autocomplete = true
vim.o.autocompletedelay = 80
vim.o.completeopt = "menuone,noselect,popup,fuzzy"
vim.o.complete = ".^5,w^5,b^5"        -- LspAttach appends ",o" (LSP)
```

**Merging several sources into one popup is `'complete'`'s job** — `.` (current
buffer), `w` (other windows), `b` (loaded buffers), `o` (omnifunc = LSP),
`F{func}` (arbitrary functions, several allowed). The `^N` after a source caps how
many candidates it may contribute.

Internally it is a **decaying time slice**: earlier sources get more time and slow
ones are demoted quickly, but all of them run. When `'complete'` contains `F` or
`o`, the timeout stretches to ~1 s for the LSP (`'autocompletetimeout'`, default
80 ms). See `:h ins-autocompletion`.

The LSP is wired in from `LspAttach` in `lua/config/lsp.lua`:

```lua
vim.lsp.completion.enable(true, client.id, ev.buf, { autotrigger = true })
vim.bo[ev.buf].complete = ".^5,w^5,b^5,o"
```

**Prose behavior** — `noselect` means nothing is preselected. So `<CR>` is just a
newline, and a candidate is only committed after deliberately picking it with
`<C-n>`. This is the setting that prevents a stray word being inserted every time
you press Enter while writing Korean prose.

| Key | Action |
|---|---|
| (typing) | popup appears automatically after 80 ms |
| `<C-n>` / `<C-p>` · `<Tab>` / `<S-Tab>` | move through candidates (plain Tab when no popup) |
| `<CR>` | commit if one is selected, otherwise **newline** |
| `<C-y>` / `<C-e>` | commit / dismiss |
| `<C-l>` / `<C-h>` | next · previous snippet placeholder (`vim.snippet`) |
| `<C-x><C-f>` | file path completion (built-in ins-completion) |

## 2. The nine plugins

### ★ render-markdown.nvim — the heart of this config

`2.3M` · MeanderingProgrammer · [repo](https://github.com/MeanderingProgrammer/render-markdown.nvim)

Styles markdown **in place, while it stays editable**: heading backgrounds, bullet
icons, checkboxes, quote bars, table alignment, code block backgrounds.

**Why not markview.nvim**: markview unrenders the region under the cursor to show
raw source. While writing, that flickers constantly and breaks flow.
render-markdown is extmark-based, so styling survives editing, and it renders only
the visible region, which keeps it light.

- Config: `lua/config/plugins.lua`
- Toggle: `<leader>tr` (show raw markup)
- Raises `conceallevel` to 3 so markers like `**` and `#` are hidden

### conform.nvim

`2.6M` · stevearc · [repo](https://github.com/stevearc/conform.nvim)

Formatter runner.

- **Lua**: format on save (stylua)
- **Markdown**: manual only — `<leader>cf`
- **Swift**: manual only — see below

Markdown is excluded from format-on-save, and **not because of Korean text**
(verified by measurement): prettier aligns tables by display width correctly,
respects `:---:` alignment markers, and with `proseWrap=preserve` does not reflow
paragraphs.

The real reason is **normalization**. Every save rewrites list markers (`*`/`-`),
nested indentation (4→2 spaces), and `1)`→`1.`, so merely opening and saving
someone else's document or a captured note produces a diff. If automatic
formatting is preferable, delete the filetype condition in `format_on_save` in
`plugins.lua`.

Swift is manual for the same class of reason, but more severely: `swift-format` is
a reformatter that re-emits the file from the AST rather than a linter, so running
it over existing code changes 46.5% of lines (measured over a 1,630-line sample;
still 33% with rules trimmed to a minimum). It restructures things like
semicolon-joined statements, which no configuration option prevents. The style
itself is pinned by `.swift-format` at the workspace root.

`swift-format` ships inside the Xcode toolchain, so nothing needs installing. The
formatter is registered as `swift` (which invokes `swift format`) rather than
`swift_format` (which looks for a `swift-format` binary on PATH and fails here).

### fzf-lua

ibhagwan · [repo](https://github.com/ibhagwan/fzf-lua)

File and content search. **This replaced telescope.nvim + plenary.nvim (two
plugins, 5.6 MB).** The list lives in the `fzf` process rather than in Lua, so it
appears instantly regardless of file count, and `bat` provides syntax-highlighted
previews.

External dependencies: `fzf` (brew) · `fd` · `rg` · `bat`

| Key | Action |
|---|---|
| `<leader>ff` | find files (fd) |
| `<leader>fg` | search contents (ripgrep) |
| `<leader>fb` `<leader>fr` | buffers · recent files |
| `<leader>fs` `<leader>fh` | search word under cursor · help |
| `<leader>fd` `<leader>fk` | diagnostics · keymaps |
| `<leader>fz` | **resume the last search** |
| `<leader>/` | search **within the current document** (for long notes) |
| `<leader>nf` `<leader>ng` | find files · search contents in the notes folder |

Inside the window: `<C-j>`/`<C-k>` move · `<C-u>`/`<C-d>` scroll the preview ·
`<C-q>` send everything to quickfix · `<C-x>`/`<C-v>`/`<C-t>` open in a
split/vsplit/tab.

### flexoki (kepano) / lualine.nvim / nvim-web-devicons

Appearance. **The editor uses the same theme as the terminal** — the palette
matches `theme = Flexoki Light` in `~/.config/ghostty/config`, so the backgrounds
join seamlessly.

| | Ghostty | nvim |
|---|---|---|
| Background | `#fffcf0` | `#fffcf0` ✅ |
| Foreground | `#100f0f` | `#100f0f` ✅ |

Switching to dark means changing **both** — Ghostty to `Flexoki Dark`, and
`plugins.lua` to `flexoki-moon` + `background = "dark"`. (git diffs are a third
place; see `git/README.md`.)

lualine shows a **word count** in markdown buffers, Korean included.

### nvim-surround

kylechui · [repo](https://github.com/kylechui/nvim-surround)

Wrapping text. **The most frequent operation in markdown prose**, and 0.12 has no
built-in replacement.

Markdown buffers add `b`/`i`/`c`/`l` targets (`after/ftplugin/markdown.lua`) —
adding them globally would override the default `b`=`()` target while editing Lua.

| Key | Result |
|---|---|
| `ysiwb` · (visual) `Sb` | `**bold**` |
| `ysiwi` · `Si` | `*italic*` |
| `ysiwc` · `Sc` | `` `code` `` |
| `ysiwl` · `Sl` | `[link]()` |
| `dsb` / `csbi` | remove / bold→italic |

A dedicated target was necessary because pressing `ysiw*` twice does not produce
`**bold**` — the second invocation treats the attached `*` as part of the word.
`b` defaults to an alias for `()`, so `aliases = { b = false }` lets it through.

### gitsigns.nvim

lewis6991 · [repo](https://github.com/lewis6991/gitsigns.nvim)

Gutter change markers and hunk operations. The most adopted git plugin (1,764
dotfyle configs, twice the runner-up).

**Commits, log, and branches are deliberately absent** — fugitive, neogit, and
lazygit collide head-on with a workflow where Claude Code makes the commits. When
browsing is needed, fzf-lua already has git pickers.

| Key | Action |
|---|---|
| `]c` / `[c` | next · previous hunk |
| `<leader>hp` `<leader>hs` `<leader>hr` | preview · stage · reset |
| `<leader>hb` `<leader>ht` | blame this line · toggle inline blame |

Inline blame is off by default: editing a paragraph of prose marks the whole line,
which is noisy.

### zen-mode.nvim

`392K` · folke · [repo](https://github.com/folke/zen-mode.nvim)

`<leader>z` — centers the text at 88 columns and hides the UI. For long-form
writing.

**mason.nvim was removed in favor of brew.** All five tools in use are available
there, so `brew install` replaces `:MasonInstall` and `brew upgrade` handles
updates in one command. macism, fzf, rg, fd, and bat already came from brew, so

```
brew install lua-language-server markdown-oxide stylua prettier
```

| Tool | Version | Role |
|---|---|---|
| **markdown-oxide** | 0.25.12 | Markdown PKM LSP — `[[wikilink]]` completion, **backlinks**, daily notes, tags. See §5 |
| **lua-language-server** | 3.19.0 | Lua LSP |
| **stylua** | 2.5.2 | Lua formatter — on save |
| **prettier** | 3.9.6 | Markdown formatter — `<leader>cf`, manual |

Every `cmd` in `lsp/*.lua` uses a bare name (`{ "markdown-oxide" }`) — resolution
happens through PATH, so a changed install location needs no config edit.

> The old `~/.local/share/nvim/mason/` (86 MB) and the lazy.nvim-era `lazy/`
> (57 MB) have been cleaned up. The nvim data directory now holds 14 MB of
> plugins and nothing else.

### Disabled: harper-ls

`lsp/harper_ls.lua` exists but is switched off. It is an English grammar and
spelling checker (runs locally, a Grammarly alternative, maintained by Automattic)
that **does not support Korean**, so it produces noisy diagnostics in Korean
documents.

To enable it only while writing English:
```
brew install harper                   -- in the shell
:lua vim.lsp.enable("harper_ls")      -- in nvim, one-off
```
For permanent use, uncomment it in the `vim.lsp.enable` list in
`lua/config/lsp.lua`.

### Swift / Objective-C — sourcekit-lsp

Comes from the **Xcode toolchain** rather than brew (`xcrun sourcekit-lsp`). It is
therefore absent from the Brewfile, and silently inactive on machines without
Xcode or a Swift toolchain.

> **⚠ The project root is not the checkout root — monorepos diverge here.**
> sourcekit-lsp needs the directory containing `buildServer.json` (Xcode) or
> `Package.swift` (SwiftPM) as its root. Pinning it to the repository root
> **breaks every package in a repo that holds more than one** — neither file
> exists at the git root, so all Swift files fall back to default compile
> arguments and imports break. (Measured 2026-08-11: all 8 SwiftPM packages in one
> repository attached to the git root and produced only warnings.)
>
> So `lsp/sourcekit.lua` **walks upward from the file but stops at the checkout
> root.** Walking up without a bound has its own trap — layouts that place a
> worktree inside a checkout would pick up the parent's `buildServer.json` — so
> the boundary stays and only the inside is searched. For an Xcode project not yet
> configured, it falls back to the directory containing `.xcworkspace`/
> `.xcodeproj`, which makes the warning point at exactly where
> `xcode-build-server config` needs to run.

> **⚠ Within that search, `buildServer.json` beats `Package.swift` at any depth —
> nearest-wins is wrong.** A repo can have an Xcode BSP at the root *and* a nested
> SwiftPM package that Xcode builds as part of the app. If the nested
> `Package.swift` wins, that package attaches in SwiftPM mode, and an iOS-only
> package yields no host compile flags — hover and go-to-definition return `nil`
> **with no warning at all**, because finding `Package.swift` counts as
> "configured". (Measured 2026-08-14: 92% of one repo's Swift files were silently
> dead this way; pointing the same file's root at `buildServer.json` produced hover
> in 6s.) The reverse never happens: a genuine multi-package monorepo has no
> `buildServer.json` anywhere, so each package still attaches to its own
> `Package.swift`.

Xcode projects need their BSP configured once before imports resolve (SwiftPM does
not):

```bash
brew install xcode-build-server
cd <project root>          # where the .xcworkspace is = where the warning points
xcode-build-server config -workspace <name>.xcworkspace -scheme <scheme>
```

#### The build server reads `rootUri`, never the working directory

`xcode-build-server` takes everything from the BSP `build/initialize` request
(`server.py`, `build_initialize`):

```python
root_path  = uri2filepath(rootUri)                       # = the LSP root_dir
cache_path = ~/Library/Caches/xcode-build-server/<root_path with "/" → "-">
config_path = root_path/buildServer.json
```

Three consequences, all load-bearing:

- **`cmd_cwd` is pointless here, so this config does not set it.** An earlier
  version pinned it to the project root on the theory that the flag cache was keyed
  by "the directory the editor opened". It is not. (Measured 2026-08-14: launching
  nvim from one checkout and opening a file in another still hovered in 2s.) It was
  also a single value computed once at config load, so in a session spanning two
  checkouts it was wrong for most clients anyway.
- **`buildServer.json` must sit in `root_dir` itself.** An ancestor copy is never
  read — which is the other half of why the BSP has to win the root search above.
- **Per-checkout caches never collide**, since the key is the root path.

`sourcekit.lua` also reads `buildServer.json` on attach and raises an error if its
`workspace` field points outside the root. That catches a worktree created by
copying the file in: it exists, so the "missing" warning stays silent, while every
absolute path inside it still names the original checkout.

#### Worktrees: seeded flags, and putting the jumps back

Running a full `make lsp`-style setup per worktree costs an Xcode build (tens of
minutes) and gigabytes of DerivedData each — untenable if you keep ten of them.
Compile flags differ between checkouts **only by path**, so a repo-side script can
transplant the main checkout's flag cache instead (measured 2026-08-14: 80s for
`xcode-build-server config` plus seconds to rewrite → hover in 2–5s, zero builds).

The transplant leaves `seed-source` in the destination's cache directory naming the
checkout it came from. When that marker is present, `sourcekit.lua` wraps the
client's `request` and rewrites location results that land in the source checkout
back onto the same relative path here, when that file exists.

> **⚠ Why this is needed at all:** intra-module jumps already resolve correctly
> (the transplant rewrites each module's source list), but cross-module symbols are
> resolved through the *source* checkout's `.swiftmodule` and index store, so they
> return its paths. Without the remap you edit the wrong checkout believing you are
> in your worktree — silently. (Measured: intra-module `DeviceCapacityChecker` → the
> worktree; cross-module `KMServerConfig` → the main checkout.) A file that exists
> only in the source checkout is left alone, with a one-time warning.

> **⚠ Hook `client.request`, not `handlers`.** `vim.lsp.buf.definition` never
> consults the `handlers` table — `get_locations` in `runtime/lua/vim/lsp/buf.lua`
> passes its own callback to `buf_request_all`, so a `handlers` entry is silently
> ignored (measured: the remap never fired). Wrapping the client's `request` covers
> `buf.definition`, `request_sync`, and picker plugins in one place.

### Do not delete `.stylua.toml`

**stylua indents with tabs by default**, while all Lua here uses two spaces. Since
conform formats Lua on save, without this file any `:w` on a `.lua` file rewrites
the whole thing with tabs (measured: all 12 `.lua` files in this config).

Its location **inside `nvim/`** matters. stylua searches upward from the file being
formatted, and `~/.config/nvim` is a symlink to this directory — keeping the file
here means it resolves whether the buffer was opened as `~/dotfiles/nvim/...` or
`~/.config/nvim/...`. Placed at the repository root, it would not be found through
the symlinked path.

### Korean/English IME switching (macOS)

Without this, pressing `<Esc>` while typing Korean leaves the input method in
Korean, so `dd` becomes `ㅇㅇ` and normal mode stops responding.

```
brew tap laishulu/homebrew      # the actual repo is laishulu/homebrew-homebrew
brew trust laishulu/homebrew    # third-party tap, needs explicit trust
brew install macism
```

Behavior: switch to ABC on `InsertLeave`, restore the previous Korean input method
on `InsertEnter`. All of it goes through `vim.system` asynchronously, so mode
changes are not slowed down.

The Korean input method ID is **detected once at startup rather than hardcoded**
(currently Apple 2-set). Swapping input methods needs no config change.

> **⚠ Race condition.** Reading from macism takes ~50 ms (measured). Written as a
> two-stage async chain — read the current input method, then switch based on the
> result — a late callback overwrites the Korean restore with English when `i` is
> pressed immediately after `Esc` (reproduced 5/5).
> So the hot path performs no queries; a **single-slot queue** collapses everything
> down to one "last desired state", and a generation counter discards late query
> callbacks.

| Command | Action |
|---|---|
| `:ImeDoctor` | actually switches and verifies that it switches back |
| `:ImeSync` | re-detect the current Korean input method as the restore target |
| `:ImeRestoreToggle` | disable/enable Korean restore on entering Insert |

Run `:ImeDoctor` first when switching misbehaves. **Some third-party input methods
revert an externally requested ABC switch on their own** — the "restrict ABC input
method" option in one of them did exactly that (measured ~100 ms). No config can
fix that; the option has to be turned off on the input method's side.

## 5. Notes (PKM)

Note-taking arrives as **an LSP, not a plugin** (markdown-oxide). As a result no
note folder path is hardcoded anywhere in this config.

### The vault is located by a root marker

markdown-oxide walks upward from the buffer looking for `.moxide.toml` or
`.obsidian` and treats that as the vault root. This lets **several vaults work
simultaneously and independently**.

| Vault | Root marker | Character |
|---|---|---|
| `~/workspace/notes` | `.moxide.toml` | Notes written directly. Managed by the workspace repo |
| Obsidian vault | `.obsidian` | Read/search archive (never written to) |

> **`.git` is deliberately excluded as a root marker.** notes/ lives inside the
> `~/workspace` repository, so including `.git` would index all 716 markdown files
> in the workspace (681 in production, 30 in toolbox) and flood backlinks and
> `[[link]]` completion with project documents.

> **⚠ `root_markers` alone is not enough — `workspace_required = true` must
> accompany it.** When no marker is found, Neovim does not decline to start the
> server; it **starts it anyway in single-file mode with `root_dir = nil`.**
> Measured (2026-08-11, nvim 0.12.4): opening a markdown file outside any vault
> (another repository's `CLAUDE.md`) attached markdown-oxide with `root_dir=nil`
> even though both the `.moxide.toml` and `.obsidian` searches returned `nil`.
> With the flag added, that file gets zero attachments, while files inside the
> vault still attach with `root_dir=~/workspace/notes` (confirmed both ways).

Creating a new vault is a matter of dropping an empty `.moxide.toml` into the
folder. The nvim config is not touched.

```
~/workspace/notes/
  .moxide.toml     daily_notes_folder = "daily"  ·  dailynote = "%Y-%m-%d"
  inbox/           quick capture, unsorted
  daily/           daily notes
```

### Keymaps

| Key | Action |
|---|---|
| `<leader>nn` | new note (prompts for a name → `~/workspace/notes/<name>.md`) |
| `<leader>nf` / `<leader>ng` | find note files / search note contents |
| `<leader>nt` / `<leader>ny` | today's / yesterday's daily note |
| typing `[[` | note title completion (built-in completion) |
| `gd` | follow link |
| **`grr`** | **backlinks** — notes referencing this one |
| `gO` | heading outline |

`<leader>nt` / `<leader>ny` map to `:LspToday` / `:LspYesterday`, which the server
registers **per buffer**, so they only work in markdown buffers. Open a note first
if you want them elsewhere.

> **Backlink caveat**: `grr` finds "links pointing at this file" when the cursor is
> in the **body**. On a title heading line (`# Title`) it instead finds "references
> to that heading", which gives different results.

### Worth knowing

- Wikilinks work correctly with Korean filenames (verified)
- `unresolved_diagnostics` is enabled, but diagnostics for broken `[[links]]` were
  never observed. Do not count on it — it may need `.moxide.toml` tuning or a
  question upstream

## 6. Markdown editing settings

In `after/ftplugin/markdown.lua`. It has to be under `after/` because Neovim's
runtime `ftplugin/markdown.vim` does a `setlocal shiftwidth=4` —
`~/.config/nvim/ftplugin/` loads earlier and would be overwritten.

| Setting | Value | Reason |
|---|---|---|
| `wrap` + `linebreak` | on | fold long paragraphs on screen without breaking mid-word |
| `breakindent` | on | wrapped lines keep their indent, so lists stay intact |
| `textwidth` | 0 | no hard wrapping. Korean word units are long and make diffs messy |
| `number` | off | distracting while writing |
| `shiftwidth` | 2 | prettier and Obsidian convention |

`j`/`k` move by **visual line** (`gj`/`gk`), except with a count — `3j` moves by
real lines, which is what keeps relative line numbers meaningful.

| Key | Action |
|---|---|
| `]]` `[[` | next · previous heading |
| `<leader>ts` | toggle spell check (English) |
| `<leader>tr` | toggle markdown rendering |
| `gO` | document symbols = outline (markdown-oxide) |

## 7. Operations

```lua
:lua vim.pack.update()                      -- update everything (<leader>pu)
                                            --   review the diff, :w to confirm / :q to cancel
:lua vim.pack.update(nil, {offline = true}) -- list installed plugins and status (<leader>ps)
:lua vim.pack.update({ "fzf-lua" })         -- one plugin
:lua vim.pack.del({ "name" })               -- remove
```

- **Never delete a plugin directory by hand** — the lockfile goes out of sync and
  it is reinstalled on the next start
- To add one: a line in `vim.pack.add` in `lua/config/plugins.lua`, then restart
- Plugins live in `~/.local/share/nvim/site/pack/core/opt/`
- `nvim-pack-lock.json` is generated in this directory → committing it reproduces
  identical revisions on other machines

### Limits of vim.pack

The built-in documentation marks it **experimental** (`:h vim.pack`,
pack.txt:211). There is no event- or filetype-based lazy loading, so everything
loads at startup. At 31 ms for seven plugins that is fine, but past roughly thirty
plugins lazy.nvim starts to win.

## 8. History

`nvim/` began as a standalone repository at `~/.config/nvim`. It was moved into a
subdirectory of dotfiles with `git mv`, so commits from before the move are still
reachable via `git log --follow nvim/<file>`.
